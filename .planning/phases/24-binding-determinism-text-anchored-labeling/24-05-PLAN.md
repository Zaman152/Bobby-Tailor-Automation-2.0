<objective>
Stop re-inventing the naming library on every run. Persist the vocabulary a project derived
and reuse it, so the deterministic wall classifier's object list stops changing underneath it.

Purpose: plan 24-02 made the wall-class DECISION deterministic. It cannot make it deterministic
end to end, because `map_wall_classes_from_library`'s object list comes from
`_wall_objects_from_vocabulary(vocabulary)` (fusion.py:1361) and that vocabulary is re-derived
from the API by `_build_project_vocabulary` (takeoff_pipeline.py:4216-4277) on every single run.
Defect F3 is exactly this: run 1 produced `Metal Downspout`, `Metal Stair`, `Aluminum Storefront`
and `Pipe Handrail`; run 2 produced `Metal Downspouts`, `Metal Stairs`,
`Aluminum Storefront/Curtain Wall`, `Roof Hatch`, `Roof Insulation`, `Vapor Barrier`,
`Drive-In Overhead Door` and `Pre-Engineered Metal Canopy`. The deterministic mapper is
deterministic given its object list; the object list is not.

Plan 24-03 folded the name FORM. This plan stabilises the CONTENTS.

**It also pays for plan 24-08.** The project-level passes were **$0.422 of run 2's $0.599 —
70% of the run**. Removing them on a repeat run funds the ensemble wire-up plan 24-08 needs, so
the phase does not raise steady-state run cost. 24-RESEARCH section 7.3.2 asks for the two to be
paired; this plan is the funding half.

**Resolved here: 24-RESEARCH Open Question 2 — per-project or per-project-type scope?**
The recommendation was per-project for determinism, with per-type retained as a suggestion
source. Reading the schema settles HOW: `learning_vocabulary`
(`learning/store.py:134-144`) has **no `project_key` column** — it is keyed
`UNIQUE(project_type, raw_pattern, canonical_name, unit)`, scoped by type with NULL meaning
global. Adding a project key to it would require rebuilding that UNIQUE constraint, which is a
destructive migration, and 24-RESEARCH section 13 forbids one. So the resolution is a **new
additive table** carrying the per-project snapshot, created by the same
`CREATE TABLE IF NOT EXISTS` idiom `_ensure_schema` already uses for four other concerns.
`learning_vocabulary` is untouched and keeps doing its per-type accumulation job as a
suggestion source. No migration, no rewrite, no data loss.

Output: a per-project vocabulary snapshot table, a persisted-first branch in the two derivation
methods, and tests proving a repeat run makes no project-level API call.
</objective>
