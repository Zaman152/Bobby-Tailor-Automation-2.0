<objective>
Carry the canonical estimator name a schedule already prints, from the schedule reader to the
aggregator, without disturbing the prose description or any other legend.

Purpose: `coverage.json` from the saved Crow run reports 31 NOT MEASURED items, of which **16 are
"NOT reconciled by name"** — the single largest bucket of lost coverage, larger than every detection
gap combined. Up to 9 of those are door and frame rows whose quantities the engine **already
measured correctly** off the printed door schedule, and then published under a name the expected-item
list cannot match.

23-04 shipped the fix for this in the producer (`feat(23-04): one door-schedule parser, named in the
canonical estimator form`, 2026-08-03) — three days BEFORE the saved run. The name was produced.
A first-match-wins field tuple in a different module discarded it.

Output: `Doors-STL` reaches the aggregator; `Doors - Steel (door schedule)` still reaches the human
report; every non-door legend resolves exactly as it does today, asserted rather than assumed.
</objective>

<tasks>

## T-29-01-01 — Emit the canonical name without displacing the description

`_calculate_from_schedule` keeps its existing `desc` resolution UNTOUCHED. It additionally reads the
row's `ITEM` and, when that value is both present and DIFFERENT from the resolved description, emits
it as `canonical_item`.

The difference test matters: a schedule whose ITEM and DESCRIPTION are the same string gains
nothing, and emitting a redundant key would put a second name into the record for no reason.

## T-29-01-02 — Whitelist it

Add `canonical_item` to `_normalize_calculated`. Copy 28-01's comment convention: state that the
whitelist is the only gate and that a key left off it is invisible downstream.

## T-29-01-03 — Prefer the printed name, below the learned one

`normalize_item_name` gains an optional `canonical` argument. Precedence becomes:

1. learned vocabulary — a human correction must never recur
2. **the printed canonical name** — the sheet's own estimator form
3. `ITEM_NAME_MAP` — the cold-start regex floor, ordering undisturbed
4. the existing item_type / description fallback

The printed name ranks above the regex map because it is evidence from the document and the map is a
built-in guess. It ranks below learned vocabulary because a human who corrected a name outranks the
sheet.

## T-29-01-04 — Pin the seam and prove the neighbours unmoved

`tests/test_phase29_name_carry.py`:

- a door-schedule legend row carrying both names reaches the aggregator as `Doors-STL`
- the prose `Doors - Steel (door schedule)` is still present for the report
- a legend row with ONLY a description resolves exactly as before (no canonical, no change)
- a legend row whose ITEM is a tag (`A-1`) and whose DESCRIPTION is prose does NOT publish `A-1`
  as an item name — the guard against the naive reorder, asserted directly
- learned vocabulary still beats the printed canonical name
- non-vacuity: each assertion is confirmed RED against the pre-change code before being kept
